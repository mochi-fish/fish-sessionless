# 0008. 水位做在压缩代理的 fork 里

状态：采用

## 背景

历史越来越长，每次请求越来越贵。要给每次请求带的历史设上限，越线时让她压缩。

能做的地方：宿主自带的压缩、再装一个压缩插件、在现有的压缩代理（billion-context）里加。

- 宿主自带的压缩会让别的模型替她写摘要。
- 再装一个压缩插件，两个压缩写手会互相打架。
- 现有的代理已经有她自己压缩、搜索、展开旧块的工具，账本里留着原文。缺的是：按会话设上限、不代写、截断只认真用量、换模型后的误判修正、中文的催压和工具说明。

上游维护者对这类改动的取舍和我们不完全一样（上游偏编程任务，我们偏长期陪伴）。

## 决定

- 用 billion-context 的 fork（trillion-context）做水位，所有新开关缺省关；不配时出站字节和上游一样。
- 中文规则包作为单独的包发（第一批 0.2），代理每次请求现读。
- 问题照样报给上游；能合的修复发 PR；上游的修复挑着并进 fork。
- 越线只催她自己压；截断是兜底，只认提供方报的真用量。
- 上限分档往下调；换模型和调上限分开做。

## 后果

- 摘要一直是她自己写的。
- 要维护一个 fork：上游每次发版要挑、要合、要重跑整套测试。
- fork 的开关多，每个都要有「关着时逐字节等于上游」的测试。
- 按 billion-context 许可的附加条款，要在文档里标明用了它（见 README 和 THIRD-PARTY-NOTICES）。
